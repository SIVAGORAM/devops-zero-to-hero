# Day 02: AWS IAM (Identity and Access Management) Deep Dive

Welcome to Day 2! Today we are learning about the absolute most important security service in AWS: **IAM (Identity and Access Management)**. 

If you do not understand IAM, you cannot be a Cloud DevOps Engineer. We will learn the theory, and then jump straight into the AWS Console for a hands-on practical lab.

---

## 1. The Bank Analogy (Why do we need IAM?)

Imagine a massive Bank. Inside this bank, there are many different areas: the front desk, the employee break room, the vault, and the manager's office.

When you walk into the bank, the security guard checks two things:
1. **Authentication (Who are you?):** Are you a customer? Are you an employee? The guard checks your ID.
2. **Authorization (What can you do?):** Just because you are a customer (authenticated), does that mean you can walk into the bank vault and take money? Absolutely not! You only have *authorization* to go to the teller desk. The Bank Manager, however, has authorization to open the vault.

**AWS works exactly the same way.** AWS has hundreds of "rooms" (services like EC2, S3 storage, Databases). IAM is the security guard that controls exactly *who* can log in, and exactly *what* they are allowed to do.

---

## 2. The Danger of the Root Account
When you first created your AWS account on Day 1, you created the **Root Account**. 

Using the Root account is like walking around the bank with the master key to every single door, vault, and security camera. If a hacker steals your Root password, they can delete your entire company's database and rack up massive bills.

**The Golden Rule of DevOps:** Never use the Root user for daily tasks. Instead, we use IAM to create limited "Users" for ourselves and our teammates.

---

## 3. The 4 Pillars of IAM

IAM is built on four core concepts. You must memorize these:

1. **Users:** A specific person or service (e.g., `John-DevOps` or `test-user-01`). This handles the *Authentication* (username/password).
2. **Policies:** JSON documents that define permissions (e.g., "Allow deleting S3 buckets"). This handles the *Authorization*.
3. **Groups:** A collection of Users. If 5 new developers join the company, you don't want to attach 50 policies to each of them manually. You create a `Developers` Group, attach the policies to the Group, and simply drop the 5 users into that group!
4. **Roles:** Temporary permissions. While Users and Groups are for people, Roles are for services. For example, if a developer working in a private cloud (on-premise) needs temporary access to an AWS Database service, they assume a Role. Roles are strictly used for temporary, secure access.

## 4. Hands-On Lab: Mastering IAM in the AWS Console

Let's put this into practice. We are going to create a user, prove they have no permissions, and then grant them access.

### Step 1: Create an IAM User
1. Log in to the AWS Console using your **Root Account**.
2. In the search bar at the top, type **IAM** and click on it.
3. On the left-hand menu, click **Users** $\rightarrow$ **Create user**.
4. **User name:** `test-user-01`
5. Check the box for **Provide user access to the AWS Management Console**.
6. Select **I want to create an IAM user**.
7. Password: Select **Autogenerated password** (This is a best practice so you can force the user to reset it).
8. Check **User must create a new password at next sign-in**. Click Next.
9. For permissions, leave it completely blank for now. Click Next. *(Note: You will notice AWS automatically attaches a default policy called `IAMUserChangePassword`. This is what allows the user to reset their password later).*
10. Click **Create user**.
11. **CRITICAL:** Click **Download .csv** or copy the login URL, Username, and Password. You will need these to log in!

### Step 2: Test the User's (Lack of) Permissions
By default, newly created IAM users have **Zero Permissions**. Let's prove it.

1. Log out of your Root Account.
2. Open a new tab and paste the **Console sign-in URL** you copied in Step 1.
3. Log in with `test-user-01` and the autogenerated password. (It will force you to create a new password).
4. Now you are logged in as `test-user-01`. Search for **S3** (AWS Storage) in the top bar.
5. Try to click "Create bucket". 
6. **Result:** You will get a red **Access Denied** error! The user is authenticated (logged in), but has NO authorization (policies) to use S3.

### Step 3: Attaching a Policy
Let's give our user the power to use S3.

1. Log back in as your **Root Account** (or an Admin account).
2. Go to **IAM** $\rightarrow$ **Users** $\rightarrow$ click on `test-user-01`.
3. Click the **Add permissions** dropdown $\rightarrow$ **Add permissions**.
4. Select **Attach policies directly**.
5. In the search box, type `AmazonS3FullAccess`. Check the box next to it.
   *(Note: This is an AWS-Managed policy. You can also write your own custom policies in JSON format. For example, here is a custom JSON policy that gives access to a specific S3 bucket—we will go deep into this in future classes!)*
   ```json
   {
       "Version": "2012-10-17",
       "Statement": [
           {
               "Effect": "Allow",
               "Action": "s3:*",
               "Resource": "*"
           }
       ]
   }
   ```
6. Click **Next** $\rightarrow$ **Add permissions**.
7. Now, if you log back in as `test-user-01`, you will be able to successfully create, update, and delete S3 buckets!

### Step 4: Creating and Managing IAM Groups
If a junior developer joins, creating policies manually takes too much time. Let's create a Group.

1. In the IAM Dashboard, click **User groups** on the left menu.
2. Click **Create group**.
3. **User group name:** `Development-Group`
4. In the "Add users to the group" section, check the box next to `test-user-01`.
5. In the "Attach permissions policies" section, search for and select `AmazonS3FullAccess`.
6. Click **Create user group**.

**Why is this powerful?**
Tomorrow, if 10 new developers join the company, you just create their usernames and drop them into the `Development-Group`. They will instantly inherit the S3 Full Access policy. If the developers ever need database access, you just add the Database policy to the *Group*, and all 10 developers are instantly updated.

---

## 🎯 Day 02 Summary
- **Authentication** is who you are (IAM User).
- **Authorization** is what you can do (IAM Policy).
- 🗣️ **Interview Question:** *"Do you use the Root User in your daily tasks?"* 
  - **Answer:** *"No. As a DevOps Engineer, we never use the Root user. For every team member, we create an IAM user and grant them permissions strictly according to their specific requirements."*
- **Groups** save DevOps engineers hundreds of hours of manual work by managing permissions for teams all at once.
