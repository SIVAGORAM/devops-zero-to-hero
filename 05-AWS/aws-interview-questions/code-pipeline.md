# AWS CodePipeline Interview Questions

AWS CodePipeline is the orchestrator of the CI/CD lifecycle in AWS. These questions test your ability to design end-to-end automated deployment workflows, handle approvals, and integrate various tools.

### 1. What is AWS CodePipeline?
**Answer:** AWS CodePipeline is a fully managed continuous integration and continuous delivery (CI/CD) service that automates your release pipelines for fast and reliable application and infrastructure updates. It orchestrates the flow of code from source control through build, test, and deployment phases.

### 2. How does CodePipeline work?
**Answer:** CodePipeline orchestrates a flow of code changes through multiple "Stages" (like Source, Build, Test, Deploy). As code moves through the pipeline, CodePipeline triggers "Actions" (like triggering CodeBuild or CodeDeploy) in a specific sequence, automating the entire software delivery lifecycle from Git push to Production.

### 3. Explain the basic structure of a CodePipeline.
**Answer:** A CodePipeline consists of:
* **Stages:** Logical phases of the pipeline (e.g., Source, Staging, Production).
* **Actions:** The actual tasks performed within a stage (e.g., fetching code, running a shell script, deploying to ECS).
* **Transitions:** The links between stages. You can enable or disable transitions to pause the flow of artifacts to the next stage.

### 4. What are Artifacts in CodePipeline?
**Answer:** Artifacts are the output files (e.g., source code, compiled binaries, Docker images) generated by an action. CodePipeline securely stores these artifacts in a designated Amazon S3 bucket and passes them as input to subsequent actions downstream in the pipeline.

### 5. Describe the role of the Source stage in CodePipeline.
**Answer:** The Source stage is always the first stage. It connects to a version control system (like AWS CodeCommit, GitHub, or Bitbucket) or an S3 bucket. It monitors for changes (e.g., a new commit to the `main` branch), downloads the source code, packages it as a Source Artifact, and triggers the pipeline execution.

### 6. How can you prevent unauthorized changes to the pipeline?
**Answer:** You enforce strict **AWS IAM** policies. You grant the pipeline its own Service Role to execute actions (Principle of Least Privilege). You also restrict human IAM users from modifying the pipeline configuration or manually executing the pipeline, enforcing that all changes must go through automated GitOps workflows.

### 7. Can you explain the concept of a Manual Approval action?
**Answer:** A Manual Approval action pauses the pipeline execution at a specific stage (usually right before deploying to Production). It sends an Amazon SNS notification to a manager or QA lead. The pipeline will remain paused until the designated approver logs into the AWS Console and explicitly approves or rejects the release.

### 8. What is a Webhook in CodePipeline?
**Answer:** A webhook is an HTTP callback mechanism used to integrate third-party source providers (like GitHub). Instead of CodePipeline constantly polling GitHub to see if code has changed, GitHub sends an immediate webhook POST request to CodePipeline the exact moment a commit is pushed, triggering the pipeline instantly.

### 9. How can you parallelize actions in CodePipeline?
**Answer:** Within a single Stage, you can define multiple actions to run concurrently rather than sequentially. For example, in the "Test" stage, you can run an action for Unit Tests, an action for Security Scanning (SAST), and an action for Linting all at the exact same time, massively speeding up pipeline execution.

### 10. What's the difference between AWS CodePipeline and AWS CodeDeploy?
**Answer:** AWS CodePipeline is the **Orchestrator**; it manages the overarching workflow (Source $\rightarrow$ Build $\rightarrow$ Deploy). AWS CodeDeploy is an **Execution Engine**; it handles the specific, final task of actually installing the code onto EC2 instances or Lambda functions. CodePipeline calls CodeDeploy during the Deploy stage.

### 11. Describe a scenario where you'd use a Custom Action in CodePipeline.
**Answer:** You use Custom Actions when you need to integrate a third-party tool that doesn't have native AWS support. For example, if you want your pipeline to trigger a specialized load-testing suite hosted on an on-premises server, you create a Custom Action that puts a job in a queue for your on-prem worker to process.

### 12. How can you handle different deployment environments (e.g., Dev, Test, Prod) in CodePipeline?
**Answer:** You handle this by creating multiple deployment stages in a single pipeline. 
* Stage 1: Deploy to Dev (Automatic)
* Stage 2: Integration Tests 
* Stage 3: Manual Approval
* Stage 4: Deploy to Prod (Automatic after approval)
Alternatively, for complete isolation, you can build completely separate pipelines for each branch/environment.

### 13. Explain how you would set up automatic rollbacks in CodePipeline.
**Answer:** CodePipeline does not have a native "rollback pipeline" button. Automatic rollbacks are handled by the underlying deployment provider (like **AWS CodeDeploy** or **AWS CloudFormation**). You configure CloudWatch Alarms; if an alarm breaches during the deployment stage, the deployment provider automatically halts and rolls back, and CodePipeline marks the stage as "Failed."

### 14. How do you handle sensitive information like API keys in your CodePipeline?
**Answer:** You must never hardcode secrets in the pipeline configuration or source code. Instead, store them in **AWS Secrets Manager** or **AWS Systems Manager (SSM) Parameter Store**. During the Build or Deploy actions, the compute environments dynamically fetch these secrets using IAM roles.

### 15. Describe Blue-Green deployment and how it can be achieved with CodePipeline.
**Answer:** Blue-Green deployment runs two identical environments to achieve zero-downtime releases. In CodePipeline, you configure the Deploy action to use AWS CodeDeploy with a Blue/Green configuration. CodePipeline hands the artifact to CodeDeploy, which provisions the Green environment, shifts traffic at the Load Balancer, and then terminates the Blue environment.

### 16. What is the difference between a Pipeline and a Stage in CodePipeline?
**Answer:** The **Pipeline** is the entire end-to-end CI/CD workflow (the whole assembly line). A **Stage** is a distinct, logical grouping of actions within that pipeline (a single workstation on the assembly line, like "Build" or "Deploy").

### 17. How can you incorporate testing into your CodePipeline?
**Answer:** You incorporate testing by adding a dedicated "Test" stage containing **AWS CodeBuild** actions. The CodeBuild action pulls a `buildspec.yml` that executes your unit testing frameworks (e.g., JUnit, PyTest). If the tests fail (returning a non-zero exit code), CodePipeline halts the release.

### 18. What happens if an action in a pipeline fails?
**Answer:** If an action fails (e.g., a unit test fails or a deployment times out), CodePipeline immediately halts the execution of that specific pipeline run. It marks the stage as "Failed," prevents the artifact from transitioning to the next stage, and can trigger an Amazon SNS alert to notify the DevOps team.

### 19. Explain how you can create a reusable pipeline template in CodePipeline.
**Answer:** You create a reusable pipeline by defining the entire CodePipeline structure (Stages, Actions, IAM Roles, S3 Artifact Buckets) as Infrastructure as Code using **AWS CloudFormation** or **Terraform**. This allows you to stamp out identical CI/CD pipelines for 50 different microservices instantly.

### 20. Can you integrate CodePipeline with on-premises resources?
**Answer:** Yes. For source control, you can integrate with an on-premises GitHub Enterprise server. For deployment, you can use AWS CodeDeploy configured with on-premises instances (via the CodeDeploy Agent), allowing you to use AWS CodePipeline to orchestrate deployments to your own physical data center.
